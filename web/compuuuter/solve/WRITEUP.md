# compuuuter — разбор

## Приложение

Маленький потоковый «граф-компьютер». Каждая нода — это

```json
{ "id": 1, "type": 2, "args": [10, 11] }
```

где `type` выбирает числовую операцию (`const`, `add`, `sub`, `mul`, `xor`,
`and`, `or`, `shl`, `shr`, `mod`), а `args` — id нод, чьи выходы читаются. Граф
можно загрузить, пропатчить, вычислить и прочитать результаты.

Есть скрытый опкод **`type 1337`**, чей выход — байты флага как little-endian
целое. Пользоваться им «не положено»: `compute` начинается с guard, который
отклоняет любую ноду с `type == 1337`. А `patch` такой проверки **не делает** —
это «просто правка».

## Баг: TOCTOU между проверкой и вычислением

```python
def compute(nodes):
    guard(nodes)                    # TIME OF CHECK: ни одной ноды с типом 1337
    nmap = {}
    for node in nodes:              # строим индекс (держит живые ссылки)
        nmap[node["id"]] = node
    ... evaluate ...                # TIME OF USE: читает node["type"] вживую
```

Guard и вычисление разнесены во времени, а `patch` может изменить ноду **на
месте** (тот же объект, на который ссылается таблица) из другого запроса. Если
переключить `type` выходной ноды на `1337` *после* прохождения guard, но *до*
того как вычисление дойдёт до неё — guard её не видел, а вычисление спокойно
выполнит опкод флага.

Проблема одна: у нормального графа окно между проверкой и использованием —
микросекунды. Его надо растянуть.

## Секундомер: hash flooding питоновского dict

Индекс нод — обычный `dict` по id ноды. Python **не** рандомизирует хеши целых:
на 64-битном CPython для неотрицательного `n`

```
hash(n) == n % (2**61 - 1)          # 2**61-1 = 2305843009213693951
```

Значит у **каждого** id вида `BASE + k*(2**61 - 1)` *один и тот же* хеш. В dict
ключи с равным хешем делят слот и одну и ту же последовательность проб, то есть
схлопываются в одну цепочку коллизий (ресайз не помогает: полный хеш одинаков, в
большей таблице они снова коллизируют). Вставка и поиск `n` таких ключей — это
**O(n²)**. Тысячи нод-наполнителей превращают прогон в секунды — этого с запасом
хватает, чтобы успеть послать `PATCH`.

Замеренное время всего `compute` (параметр `N` в `solve.py`):
N=10000 ≈ 1.3 с, N=15000 ≈ 2.8 с, N=20000 ≈ 5.1 с.

## Эксплоит

1. Загружаем граф: `N` нод-наполнителей `const` с id `7 + k*(2**61-1)`
   (`k = 0..N-1`) — секундомер — плюс безобидная выходная нода `id=1`,
   поставленная последней, чтобы считаться после всего наполнителя.
2. В одном потоке стреляем `POST /compute`. Guard проходит (на 1337 никто не
   ссылается), затем начинается медленная O(n²) сборка/вычисление.
3. Через ~0.3 с (guard давно отработал, сборка молотит) шлём
   `PATCH {"id":1,"type":1337,"args":[]}`.
4. Когда вычисление наконец дойдёт до ноды 1, оно прочитает `type == 1337`,
   выполнит опкод флага, и результат ноды 1 — целое с байтами флага. Переводим
   обратно в little-endian байты.

```
$ python3 solve.py http://<host> 6000
ctfcup{...}
```

Если `compute` успел завершиться до того, как долетел патч — просто повторить
(или поднять `N`).

## Фикс

Перепроверять внутри критической секции / делать снимок графа под локом перед
вычислением и прогонять в `patch` тот же guard. Плюс ограничить размер графа или
хешировать таблицу так, чтобы id, выбранные атакующим, не схлопывались в один
бакет (именно hash flooding делает окно выигрываемым).
