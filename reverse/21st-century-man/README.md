## Идея

Задание на реверс FPGA‑битстрима с небольшой дозой комплексного анализа.

Флаг — текст `ctfcup{3ab5e98041a0f89b67273ba39b17b37a}`, «зашитый» в аналитическую функцию.
Генератор [src/generator/lemniscate](src/generator/lemniscate) рендерит строку шрифтом
(DejaVu Sans Bold) в многоугольник и строит рациональную функцию

```text
g(z) = ∏_j (z − a_j) / ( c · ∏_k (z − b_k)^{m_k} )
```

с 2940 нулями `a_j`, расставленными чуть внутри букв (взвешенные точки Лежа, так что |g|
выравнивается вдоль контура), и 377 полюсами `b_k` (суммарной кратности 2292) в дырках букв
и промежутках между ними, чтобы те не «заплывали». Уровень `c` подобран так, что множество
`{|g| < 1}` — это сглаженный текст, а всё остальное в прямоугольнике — `{|g| > 1}`. Это
лемниската (теорема Гильберта): по принципу минимума модуля у `{|g| < 1}` нет лишних
компонент. Как выглядит `{|g| < 1}` итоговой модели — в
[src/generator/ice40/model/flag_preview.png](src/generator/ice40/model/flag_preview.png).

Устройство ([src/generator/ice40](src/generator/ice40), тот же байтовый протокол, что и у
Versal‑варианта [src/generator/dsp58](src/generator/dsp58)) принимает по UART точку `x, y`
(fp32 LE) и отвечает `g(x + iy)` в блочной плавающей точке: мантиссы `re, im` (fp32,
`max(|re|,|im|) ∈ [1, 2)`), экспонента `e` (int32) и флаги (`0x01` — |g| < 1, `0x02` — полюс,
`0x04` — нуль, `0x80` — битая контрольная сумма запроса). FPU внутри нет: координаты в Q4.28,
коэффициенты в ROM в Q4.12 (текст отмасштабирован в полосу
`[-3.9, 3.9] × [-0.1275, 0.1275]`), произведения в Q2.30 с общей экспонентой, четыре параллельных
сдвигово‑суммирующих умножителя, деление восстанавливающим делителем; ~190 000 тактов на точку.
Коэффициенты лежат в 26 блоках BRAM (`SB_RAM40_4K`, 13 групп по два: re и im), кратности
полюсов — логической таблицей. Чип занят на 96 %.

Проверялка (`src/problem`) делает ровно то, что написано: если нарисованная фигура не замкнута
или не ограничивает область — «Cannot determine validity»; иначе берёт **случайную** точку
внутри фигуры, спрашивает устройство и показывает «Possibly valid», если `|g| < 1`, и
«Definitely invalid» иначе. Проверенную точку она не показывает: даже с живой платой флаг
пришлось бы нащупывать по одной точке, а платы у участников нет.

## Решение

Весь путь — офлайн, по битстриму, с опциональной помощью симулируемого устройства.

1. **Нетлист из битстрима.** `iceunpack g.bin` даёт текстовую конфигурацию,
   `icebox_vlog -s -p pins.pcf` — Verilog‑нетлист чипа: каждая LUT как `assign`, каждый
   триггер как `always`, 29 `SB_RAM40_4K` с параметрами `INIT_*`. Три из них — FIFO UART
   (8‑битный режим), 26 — ROM коэффициентов (режим 256×16).

2. **Запустить устройство (не обязательно, но полезно).** Нетлист вместе с
   `ice40/cells_sim.v` из yosys прогоняется через `write_cxxrtl` (сначала `opt_mem`: порт
   записи с константным клоком роняет экспорт), получается C++‑модель, которую
   [tools/run_device.sh](src/generator/ice40/tools/run_device.sh) крутит как UART‑устройство на
   pty. Точка считается ~3 с, так что скан картинки целиком (десятки тысяч точек) нереален, но
   проверялка с ним работает, и его можно спрашивать прицельно (шаг 4).

3. **Вытащить коэффициенты.** ROM — 13 групп по 256 32‑битных слов `{im, re}`, обе половины
   Q4.12; каждая группа — два BRAM, один хранит re, другой im (im легко отличить: |im| < 0.13,
   старшие биты — знаковое расширение). Внутри BRAM 16 бит слова лежат в физическом порядке
   колонок iCE40 — по bit‑reversal 4‑битного индекса (бит `p` на позиции `rev4(p)`), адреса
   сохранены. Все 26 BRAM висят на одних и тех же шинах адреса и enable, группа выбирается
   выходным мультиплексором, который ABC перемолол до неузнаваемости, поэтому пары re/im
   восстанавливаются по данным: нули лежат на контуре букв в нескольких тысячных друг от
   друга, и только при правильном спаривании у большинства точек есть близкий сосед.
   Hill‑climbing по числу точек с соседом ближе ~1/60 высоты полосы сходится к правильному
   спариванию с любого старта (проверено по модели: 2951 из 2959 точек восстановлены точно,
   остальные 8 — точки с нулевой координатой, отброшенные как пустые слова).

4. **Прочитать текст.** Нули сами по себе рисуют буквы; картинка локальной плотности точек
   (внутри штриха вклад дают оба его края) читается уже без устройства — `solve.py` пишет её в
   `flag.png`. Для чистой картинки используется устройство: запрос ровно в изолированной точке
   возвращает флаг ZERO или POLE (так отделяются полюса), а несколько сотен случайных
   запросов дают `log|g|`, откуда МНК восстанавливает кратности полюсов (целые) и уровень `c`;
   после этого `{|g| < 1}` рисуется точно (`flag_exact.png`).

[solve/solve.py](solve/solve.py) делает шаги 3–4 (`python3 solve.py design.v flag.png
[--port /dev/pts/N]`); шаги 1–2 — `make cxx device` в `src/generator/ice40`.

### Сборка задания

```sh
cd src/generator/lemniscate && cargo build --release
./target/release/text_lemniscate build 'ctfcup{3ab5e98041a0f89b67273ba39b17b37a}' \
    -d 2940 --holes keep --spacing 0.3 --no-map --model ../ice40/model/flag_raw.json
cd ../ice40
make                     # scale_model.py -> gen_rom.py -> yosys -> nextpnr-ice40 -> icepack -> build/g.bin
make cxx device          # битстрим -> C++ -> устройство на pty (build/g_uart), для проверки
make check               # 200 случайных точек против double-precision модели
cd ../../problem && ./build.sh     # сборка в Docker, в бинаре нет путей хост-машины
```

Сборка идёт в Docker‑образе с OSS CAD Suite (`Dockerfile`), `make NATIVE=1 …` — тулами из
`$PATH`. Степень 2940 выбрана по ёмкости BRAM UP5K: 3317 слов ROM = 26 блоков, ещё 3 занимают
FIFO. `--holes keep` оставляет дырки букв (по полюсу в каждой) вместо прорезей: с ~75 нулями
на глиф только так текст остаётся читаемым.
